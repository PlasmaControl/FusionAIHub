# Label tables

Label data lives here; readers and producers live in `src/labelmaker` and
`scripts/labelmaker`. The user's convention is one directory per label category:

```text
data/events/<category>/
  README.md
  raw/                         # the original provided list, untouched
  format/                      # the raw table reformatted into ONE common schema
    <stem>.csv
    <stem>.meta.json
  extend_<model>/               # what this producer yields on the 500 project shots
    recommender_v1.csv
    recommender_v1.meta.json
```

`raw/` keeps each original exactly as provided, in its original format. No code
edits, sorts, deduplicates, or converts units in these files. The RWM originals
were moved byte-identically from the category root (the versions at `6de489d`).

`format/` is the single common representation shared by every dataset. Deterministic
raw-to-format adapters in `scripts/labelmaker/labels_format.py`, driven by
`tables.yaml`, produce it. `src/labelmaker/events/databases.py` reads **only** these
format CSVs; the original's column names and units are converter inputs.

`extend_<model>/` is **one directory per producing model/source**, so any number of
producers can process the same category. Each contains that producer's output on
the 500 `recommender_v1` shots, in the same schema. The directory names the producer;
the filename names the shot list. Each directory is regenerated by that producer's
task using `scripts/labelmaker/labels_extend.py`. A category with no producer yet
has **no** `extend_*` directory; task F's roadmap generator reports `not_started`.
The old unqualified `extend/` directory is not used.

The twelve category directories mirror the user's layout. Their READMEs preserve
the user's authored content or follow the same section template, with technical
inventory and lexicon mappings under `Tables`. Pending IDs are explicit. Directory names are prose; the join key is the phenomenon ID in
`src/labelmaker/events/lexicons.yaml`. H/L/I-mode intervals, q-min bands, and WPQH
must get their own IDs in their producer tasks; `lh` is a transition and `qh` is
QH-Mode, so neither is silently reused for those distinct labels.

## Common schema

`databases.FORMAT_COLUMNS` and `validate_format` define this CSV projection of the
events schema once. Columns are required in this order, with no extra columns:

| Column | Type | Meaning |
|---|---|---|
| `shot` | integer | Shot number |
| `t0_s` | finite float | Start time, seconds |
| `t1_s` | finite float | End time; equals `t0_s` for a point, never smaller |
| `phenomenon` | string | Exact `lexicons.yaml` ID |
| `evidence_kind` | string | Events kind: detector, heuristic, forecast, text, human, database, model |
| `source` | nonempty string | Producing source, e.g. `database:rwm_onsets_2017` |
| `confidence` | float or empty | Probability in [0, 1]; empty means NaN/unknown |
| `attrs` | string | JSON object, possibly `{}`; no NaN/Infinity JSON literals |

Every table has `<stem>.meta.json` with `schema_version` (currently 1), `made_from`,
`made_by`, `made_at`, `n_rows`, and `n_shots`. For format tables, `made_from` contains
`raw_file` (relative to this root) and its SHA-256. For extensions, it is a list of
actual `producer`, `run_id`, and `git_sha` triples from event/source products; all
contributing runs are retained. An empty list means no matching producer provenance
was found, not that a producer ran successfully. A completed databases-only zero
scan can instead supply its verified run JSON via `--root` and `--run-id`.

Format metadata's `made_at` is the **recorded conversion revision timestamp in the
manifest**, not the execution wall clock or filesystem mtime. Update it deliberately
when revising a conversion. Regeneration uses sorted rows (duplicates retained),
sorted JSON keys, UTF-8/LF CSV, twelve decimal places, and empty NaN fields. The
CSV **and** sidecar therefore regenerate byte-identically. Extension `made_at` is
the export time; input-run provenance remains separate.

This is a projection, not a replacement for full events: coverage, diagnostic
identity, forecast horizons and per-event IDs remain in the parquet products.
Evidence kinds are preserved, so a forecast remains a forecast, never an observation.

## A listing is not a coverage claim

Curated converters write `evidence_kind=database`, `source=database:<stem>`, and
unknown confidence. Extra original columns and the table stem travel in `attrs`.
The loader preserves the format table's evidence, confidence and parsed attributes.
Every curated event and source row retains `t_cov0_s = t_cov1_s = NaN`: a list says
nothing about the interval somebody examined. A shot absent from a table gets
**no event and no source row**, and its absence is never a negative. A named shot
gets one `status=ok`, `reason=""` source row per table, with NaN coverage.

## Add a table

1. Drop the untouched original into `data/events/<category>/raw/`.
2. Add a manifest entry describing its raw columns and naming its format stem:

   ```yaml
   - stem: example_onsets              # unique; source is database:example_onsets
     dir: resistive_wall_mode
     raw_file: original.csv            # filename within raw/
     format_stem: example_onsets       # filename within format/, without .csv
     converter: csv                   # registered adapter in labels_format.py
     made_at: "2026-09-13T00:00:00Z"    # recorded conversion revision time
     phenomenon: rwm
     kind: point                      # interval uses t0_col and t1_col
     shot_col: SHOT
     t_col: TIME
     t_units: ms                       # ms or s
     attr_cols: [NTOR]
     attr_types: {NTOR: int}            # int, float, str; default str
     provenance: "Author, campaign and method"
   ```

3. Register a small adapter in `scripts/labelmaker/labels_format.py` if needed.
   The `csv` adapter handles manifest-declared point and interval CSVs; the two
   RWM tables each have a named adapter. Other original formats need their own
   adapter returning the same columns, never a loader special case.
4. Run the converter, then commit raw, format CSV, metadata, manifest, and adapter:

   ```bash
   PYTHONPATH=src python scripts/labelmaker/labels_format.py
   # Optional: --root <labels-root> --table example_onsets
   git add data/events scripts/labelmaker/labels_format.py
   ```

5. Ingest curated events with the unchanged standalone command:

   ```bash
   python -m labelmaker.run events --databases-only --root /tmp/labelmaker-example \
       --shot-file /path/to/shots.txt
   ```

`config.Paths.label_tables` locates this root; `LABELMAKER_LABEL_TABLES` overrides it
for tables too large or restricted to commit. Only commit redistributable, small
tables. The root `.gitignore` re-includes `data/events/`, so no forced add is needed.

## Extend a producer onto the 500 shots

```bash
PYTHONPATH=src python scripts/labelmaker/labels_extend.py \
    --category edge_localized_mode --producer elm_clock \
    --shot-list configs/ideate/shot_lists/recommender_v1.yaml \
    --events-root "$LABELMAKER_ROOT/events" \
    --out data/events/edge_localized_mode/extend_elm_clock/recommender_v1.csv
```

The writer reads `<shot>_events.parquet` through `read_events` and source records
through `read_sources`, without modifying them. `--producer` selects an exact
source or phenomenon ID, restricted to the category. Use the source for a single
model's output. A phenomenon selector that spans producing sources is refused
before writing: export each source separately, including logbook `text` evidence.
A single-source phenomenon export must use `extend_<actual-source>/`; only an
empty scan with no producing source can use `extend_<phenomenon>/`. Colons in source IDs become underscores
only in the directory slug (`database:rwm_onsets_2017` →
`extend_database_rwm_onsets_2017`). Producer tasks register new category IDs and
known source mappings in the extension script when their lexicon entries land.

**Size rule:** at most 50,000 selected events yields the common table above.
**More than 50,000** yields `recommender_v1.summary.csv` and
`recommender_v1.summary.meta.json` instead, with one row per requested shot:

```text
shot,n_events,t_first_s,t_last_s,t_cov0_s,t_cov1_s
```

`n_events` counts selected rows without deduplication; first/last are the minimum
start and maximum end. Zero-event shots have empty first/last times. Coverage is
the bounding range from matching successful source records, falling back to event
coverage when no successful source record exists. These bounds do not assert
continuous coverage. Unknown or missing coverage stays empty. Metadata records the
full selected event count, requested shots, missing event files, source statuses,
and the full events location. `full_events_root` is relative to `--root`
when contained there (normally `events`); external stores retain their absolute
path. A supplied run ID also records the root-relative `run_metadata` path.
Missing event files are recorded as a count, the first 20 shots, and a filename
pointing to the complete `<shot-list>.missing_event_shots.json` list beside the
CSV; the full list stays outside the compact metadata. A rerun removes the stale alternate full/summary table and its sidecar.

`n_shots` counts shots represented in the output table: event-bearing shots for a
full table, all requested shots for a summary. `n_shots_with_events` and
`n_requested_shots` keep the two quantities explicit. Missing files remain visible;
a zero count alone never establishes a successful detector run or a negative label.
