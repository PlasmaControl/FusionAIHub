## The measured problem (L12 report, `FusionAIHub-L/.superpowers/sdd/task-L12-report.md`)
Pilot 2931065_0 (A100, 8 CPUs, 6 prep workers, batch 96, AMP, 20 shots): 48.97 tiles/s; **GPU util 6.9 %**, CPU 27 %, GPU-mem 94.7 % (allocator cache — torch peak allocated 17.6 GiB). Inference phase = 49.8 % of driver wall yet the card idles: `masks.infer` per block does `tile()` (host copy into a `(n,512,512)` float32 array), `torch.from_numpy`, per-batch `_to_device` (synchronous, pageable), forward, `probs.to("cpu", torch.float32)` (synchronous D2H of `n × 2 × 512 × 512 × 4 B` = 2 MB/tile), `np.concatenate`, `stitch()` (float64 accumulation on the host), then `pipeline.describe_block` (19.3 % of wall) and prep wait (21.3 %). All 182 blocks had 10–55 tiles (< the 96 batch cap), so every block is a tiny GPU burst between long host phases; batch size cannot help. A second pilot with 1 prep worker was worse (GPU 3.8 %).

## Deliverables
1. **Profile first** (login-node V100S is fine for the profile; `--limit 3 --passes wide zoom`): `torch.profiler` + wall-clock split per block into prep-wait / H2D / forward / D2H / stitch / describe / write; a table in the report. State the numbers before changing anything.
2. **Restructure `masks.infer` + the driver's inference loop** so the GPU is the bottleneck, in this order of preference, each step with an OUTPUT-IDENTITY test (masks arrays and events frames byte-identical to the current `process_shot` on the synthetic fixtures at (0,1), (1,4), (2,2) for both passes, and on ONE real shot on CPU — the identity tests in `test_events_pipeline.py`/`test_tokeye_masks.py` are the model):
   a. **Stitch and threshold on the device**: accumulate the overlap average on the GPU (float32 is fine if the test shows identity to the stored packed masks; otherwise float64 on device), apply `PROB_THRESHOLD` and the row/col statistics there, and move only what `MaskBlock` stores (packed bool + `_row_lit` + `_col_act`, ≈ 1/32 of the float32 probs). Keep a `--probs-on-host` path for the rendered-window uint8 probabilities.
   b. **Cross-block tile pooling**: a device-side queue that concatenates tiles from consecutive prepared blocks (across channels/passes/shots) into full batches; results are scattered back per block. Pinned host memory + `non_blocking=True` + a copy stream so H2D of block k+1 overlaps the forward of block k.
   c. **Move `describe_block` off the critical path** (a second describe process or the tail pool), since it is 19 % of wall and pure CPU.
   d. Only then revisit prep: `--prep-workers` ≥ what the profile says the GPU needs (target: prep wait ≈ 0 with GPU ≥ 70 %).
3. **One pilot** (≤ 20 shots, the same 20 as L12 so the numbers compare; cold compute-node A100 via L12's `tokeye_masks.sbatch`; `--pilot` gate, exempt but reported): tiles/s, GPU util, CPU util, both memory measurements (sampled + sacct MaxRSS). Target ≥ 70 % GPU. If missed, diagnose and stop; do not submit production. If met, propose the production sizing (8 × 60 shots, `--array 0-7%2`) with CPU/mem/time from the pilot × 1.3 — proposal only; the controller submits L14.
4. Re-run the five L12 error shots (185962 185980 185982 186090 186196) in the pilot to confirm L-A's isolation fix holds under the driver.
5. Report `.superpowers/sdd/task-L14perf-report.md`: profile table before/after, identity evidence, pilot jobstats (both memory numbers), the production proposal, deviations. Update `docs/LABELMAKER.md`'s driver section.
